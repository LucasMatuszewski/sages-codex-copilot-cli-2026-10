Jak cofnąć pracę agenta?

W Copilot CLI użyj /undo lub /rewind (alias), wybierz wcześniejszy prompt, a potem Conversation only albo Conversation + files. Pierwsza opcja cofa rozmowę; druga próbuje dodatkowo przywrócić pliki zmienione przez Copilota. W VS Code użyj Restore Checkpoint; interfejs oferuje też Redo i rozgałęzienie rozmowy.

Zrób próbę na nieistotnym pliku i obejrzyj podgląd. Cofanie nie odwraca zewnętrznych akcji, np. już wypchniętego commita. Po przywróceniu sprawdź git status i git diff.

CLI może pominąć plik zmieniony później ręcznie, a także bardzo duże pliki lub długie tury. W dokumentacji GitHub opis ograniczeń cofania nie jest całkiem spójny. Traktuj Git jako niezależny punkt odzyskania.

Źródła: GitHub - rollback CLI, VS Code - checkpoints.

Assisted permissions a Autopilot - co jest czym?

W VS Code Manual, eksperymentalne Assisted i Allow all to poziomy zgód w sesji. Assisted używa modelu oceniającego wywołanie narzędzia i pyta człowieka, gdy nie zatwierdzi go automatycznie. Autopilot to tryb kontynuowania zadania, który pomija pytania o zgodę; Advanced Autopilot dodaje osobny model oceniający ukończenie. To różne funkcje.

W CLI /permissions assisted zmienia bieżącą sesję, a /permissions show pokazuje stan. W CLI 1.0.88 ustawienie defaultPermissionMode: "assisted" w ~/.copilot/settings.json może ustawić domyślny poziom dla nowych interaktywnych sesji, jeśli funkcja eksperymentalna i polityka organizacji na to pozwalają. To inne ustawienie niż VS Code chat.permissions.default.

W VS Code oba tryby są eksperymentalne i każdy działa w innym harnessie. Assisted działa tylko w Agent Host (włącz chat.assistedPermissions.enabled). Advanced Autopilot działa tylko w harnessie Local, czyli w Extension Host (włącz chat.autopilot.advanced.enabled). Dokumentacja nie podaje osobnej ceny ani nazwy modelu oceniającego Assisted, więc nie zakładaj, że jest bezpłatny.

Poziom zgód wybierasz dla bieżącej sesji w pickerze czatu. chat.permissions.default ustawia poziom dla nowych sesji; starsze chat.experimentalModePermissionsPicker nie jest już udokumentowaną instrukcją włączenia pickera. Advanced Autopilot działa podobnie jak /goal w Claude Code i Codex: agent pracuje dalej, aż osobny model uzna zadanie za ukończone. W Copilot CLI /goal uruchamia Autopilot.

Jeśli chcesz udostępnić narzędzie tylko do jednego pytania, w sesji Local otwórz Configure Tools przy polu czatu i wybierz narzędzia przed wysłaniem wiadomości. W Copilot harness wybór narzędzi w Agent Customizations zapisuje się w profilu użytkownika. Włączenie narzędzia nie oznacza automatycznej zgody na jego wywołanie.

Przykład automatycznego zatwierdzania i blokowania wybranych poleceń CLI jest w repozytorium kursu. Copilot nie odczytuje takich list z repozytoryjnego .github/copilot/settings.json.

Źródła: VS Code - approvals, VS Code - narzędzia, GitHub - komendy CLI, lokalny copilot help config 1.0.88.

Dlaczego skill nie pojawia się w IntelliJ?

Sprawdź wersję pluginu GitHub Copilot, wybrany harness i panel Customizations. Obsługa skills w JetBrains jest nadal dostępna jako wersja testowa. Repozytoryjne .agents/skills/<nazwa>/SKILL.md jest oficjalną lokalizacją skills, ale wykrywanie zależy od powierzchni i konfiguracji. Jeśli nie widać skilla w Local, sprawdź Copilot harness; nie kopiuj od razu skilla do kolejnych miejsc.

W VS Code "Local" oznacza host rozszerzenia w edytorze, a nie model uruchomiony lokalnie. Copilot harness działa na Agent Host i korzysta z Copilot SDK. Sam SDK pozwala też budować własne aplikacje z silnikiem Copilot. Copilot CLI w terminalu i JetBrains AI Assistant przez ACP to kolejne odrębne interfejsy.

Źródła: GitHub - mapa customizacji, GitHub - JetBrains, JetBrains 1.18.0, VS Code - harnesses, GitHub - Copilot SDK.

Czy zagnieżdżone AGENTS.md działają automatycznie?

W VS Code Local odczyt zagnieżdżonych plików zależy od chat.useNestedAgentsMdFiles, które jest domyślnie wyłączone. Plik główny ma osobne ustawienie chat.useAgentsMdFile. Agent Host stosuje reguły wybranego harnessu; nie przenoś ustawienia Local na wszystkie narzędzia bez testu.

Dla instrukcji przypiętych do konkretnych plików można użyć .github/instructions/*.instructions.md i applyTo. W repo kursu jest folder przykładów AGENTS.md dla Next.js i MCP. To materiały do adaptacji; same pliki w tym folderze nie stają się automatycznie instrukcjami bieżącego projektu. Poproś agenta o wskazanie, które instrukcje faktycznie zastosował do bieżącego pliku.

Źródła: VS Code - custom instructions, przykłady z repo kursu.

Gdzie trafia historia sesji?

VS Code Session Sync jest domyślnie włączone, jeśli pozwala na to polityka firmy. Sesje są synchronizowane z osobistym kontem GitHub; można wyłączyć synchronizację przez chat.sessionSync.enabled lub wykluczyć wybrane repozytoria. Jeśli synchronizacja jest wyłączona, kliknij ikonę Copilota na pasku stanu (prawy dolny róg) i wybierz Session Sync: Enable. Chronicle pomaga wyszukać wcześniejsze sesje.

Źródło: VS Code - session history.

Co może ustawić organizacja, a co zrobić lokalnie?

Administratorzy mogą zarządzać częścią polityk Copilota, MCP i enterprise plugin standards. Nie ma w dokumentacji jednego uniwersalnego przełącznika "wymagaj tego skilla wszystkim". Nowy plugin JetBrains deklaruje obsługę skills organizacyjnych, lecz dokładną ścieżkę publikacji trzeba potwierdzić dla danej powierzchni.

Bezpośrednia instalacja pluginu z repozytorium nadal działa, ale jest oznaczona jako deprecated; dla pluginów preferowany jest marketplace. Publiczne pojedyncze skills z EdukeyTeam/agent-toolbox instalujemy zgodnie z instrukcją kursu. BYOK samo w sobie nie oznacza modelu lokalnego. Praca lokalna wymaga zaplecza uruchomionego na własnym urządzeniu lub w zatwierdzonym środowisku; zgodność z polityką firmy wymaga osobnej decyzji organizacji.

Źródła: GitHub - enterprise plugin standards, GitHub - plugin CLI, VS Code - language models.

Czy Copilot indeksuje repozytorium jak Cursor?

Tak. Narzędzie semantic search szuka kodu po znaczeniu, nie tylko po słowach. Agent używa go sam, gdy to pomaga; możesz je wskazać przez #codebase.

  • GitHub i Azure DevOps: indeks buduje się zdalnie i automatycznie.
  • Inne repozytoria: indeks lokalny, pierwsze budowanie trwa kilka minut. Dla kont organizacji jest domyślnie wyłączony i włącza go polityka Copilota.
  • Pomija pliki z .gitignore, files.exclude i search.exclude. Przebudowa: Build Codebase semantic index w palecie poleceń.

Agenci coraz lepiej radzą sobie zwykłym przeszukiwaniem plików (grep, ripgrep), więc indeks najbardziej pomaga w dużych repozytoriach i przy pytaniach o znaczenie ("gdzie liczymy rabat?").

Źródło: VS Code: workspace context.

Agent Host, harnessy i praca w WSL

W VS Code agent działa w jednym z dwóch miejsc. Local (Extension Host) to domyślny czat rozszerzenia Copilot. Agent Host to osobny proces, w którym działają harnessy Copilot (Copilot SDK), Claude i Codex. Tylko w Agent Host są m.in. Assisted permissions, sesje współdzielone między oknami i zdalne uruchamianie agenta.

Agent Host działa tam, gdzie workspace. Połącz VS Code z WSL (przycisk w lewym dolnym rogu, rozszerzenie WSL): agent i jego polecenia działają wtedy w Linuksie, nie w Windows. Tak samo przy SSH; w Dev Containers to wciąż funkcja eksperymentalna.

Źródła: VS Code: Agent Host, VS Code: harnesses.

Git worktrees bez instalowania wszystkiego od nowa

Każdy worktree potrzebuje własnego node_modules. Z pnpm prawie nic to nie kosztuje: pakiety leżą w jednym magazynie na dysku, a node_modules w worktree zawiera tylko linki. Włącz globalny wirtualny magazyn w pnpm-workspace.yaml:

virtualStoreType: global

W pnpm starszym niż 11.23 to enableGlobalVirtualStore: true. Pierwsze pnpm install pobiera pakiety, w kolejnych worktree instalacja trwa chwilę. npm i Yarn nie mają takiego mechanizmu: każdy worktree to pełna instalacja.

Jeden zapisywalny magazyn tylko dla agentów, którym ufasz w równym stopniu. Pozostałe koszty worktree zostają: osobne porty serwerów, kopia .env i sprzątanie przez git worktree remove.

Źródło: pnpm: git worktrees.

Hooki: jak sprawdzić zakres działania?

Hook reaguje na zdarzenie sesji lub użycia narzędzia. Copilot CLI ma pliki .github/hooks/*.json oraz zdarzenie preToolUse. Nazwy zdarzeń, format argumentów i kod odmowy sprawdź w dokumentacji konkretnego agenta.

Skrypt zawęża działanie do wskazanej ścieżki lub komendy. Przetestuj nieszkodliwy dozwolony i blokowany przypadek. Przykłady wielonarzędziowe w bibliotece hooków wymagają dopasowania i testu w używanej wersji.

Źródła: GitHub: hooki, Codex: hooki. Stan: 05.10.2026.

Własny fork przed pierwszym pushem lub PR

W dniu 1 klonujesz publiczne repo trenera i pracujesz na lokalnym branchu. W dniu 3, zanim wyślesz branch albo utworzysz PR, przygotuj własny fork dla tego samego klona. Nie klonuj ponownie, nie resetuj plików i nie porzucaj lokalnych zmian.

Wybierz jeden wariant przygotowania forka. Wariant z GitHub CLI: w terminalu w katalogu repozytorium zaloguj się przez przeglądarkę, a następnie utwórz fork. Polecenie gh repo fork --remote ustawia Twój fork jako origin i zmienia nazwę dotychczasowego remote trenera na upstream.

gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git --hostname github.com
gh repo fork --remote
git remote -v
git remote get-url origin
git remote get-url upstream

Wariant bez GitHub CLI: na stronie repozytorium trenera w GitHub kliknij Fork i utwórz kopię na swoim koncie. Ten wariant zastępuje gh repo fork, nie wykonuj obu. W tym samym lokalnym klonie zmień nazwę remote trenera:

git remote rename origin upstream

Wybierz dokładnie jeden sposób uwierzytelnienia do własnego forka. W przykładach zastąp TWOJ-LOGIN swoim loginem i sprawdź adres z przycisku Code we własnym forku.

HTTPS: użyj wcześniej skonfigurowanego menedżera poświadczeń Git, który loguje przez przeglądarkę. Jeśli nie jest skonfigurowany, uzgodnij konfigurację z trenerem przed pushem. Dodaj origin HTTPS:

git remote add origin https://github.com/TWOJ-LOGIN/sages-codex-copilot-cli-2026-10.git

Albo SSH: użyj wcześniej skonfigurowanego klucza SSH dodanego do Twojego konta GitHub. Zamiast powyższego origin HTTPS dodaj origin SSH:

git remote add origin git@github.com:TWOJ-LOGIN/sages-codex-copilot-cli-2026-10.git

Nie wykonuj obu poleceń dodania origin. Następnie sprawdź remotes:

git remote -v

Oba warianty zachowują istniejący branch i lokalną pracę. Nie wymagają resetu ani ponownego klonowania. GitHub CLI pozostaje opcjonalne; wariant ręczny nie wymaga jego instalacji. Push wymaga działającego uwierzytelnienia Git do Twojego konta.

Sprawdź wyniki: origin musi wskazywać repozytorium na Twoim koncie, a upstream ma wskazywać https://github.com/LucasMatuszewski/sages-codex-copilot-cli-2026-10.git. Zmiana remotes zachowuje bieżący lokalny branch i pliki. Jeśli adresy są inne, wyjaśnij różnicę z trenerem przed pushem.

Przejrzyj diff, wykonaj testy i commit uzgodnionej zmiany. Dopiero potem wyślij bieżący branch do własnego forka:

git push -u origin HEAD

W tym szkoleniu standardowym celem PR jest Twój własny fork. W formularzu GitHub ustaw base repository na TWOJ-LOGIN/sages-codex-copilot-cli-2026-10, base na main, a compare na swój wysłany bieżący branch, np. moja-praca. Zastąp TWOJ-LOGIN swoim loginem i jawnie sprawdź te trzy pola przed wysłaniem. Nie kieruj PR do repo trenera bez osobnego uzgodnienia. Po gh repo fork kolejne operacje gh domyślnie wskazują upstream, dlatego cel PR sprawdzaj jawnie w GitHub. Utworzenie lokalnego brancha, push i PR to osobne kroki. Pełny przebieg: Review i CI oraz README repozytorium kursowego.

Jeśli wybierasz GitHub CLI do utworzenia PR, wskaż własne repozytorium, bazę i branch jawnie. Przykład dla brancha moja-praca; przy innej nazwie zastąp ją w poleceniu. Po utworzeniu sprawdź URL repozytorium oraz nazwy base/head w wyniku:

gh pr create --repo TWOJ-LOGIN/sages-codex-copilot-cli-2026-10 --base main --head moja-praca
gh pr view --repo TWOJ-LOGIN/sages-codex-copilot-cli-2026-10 --json url,baseRefName,headRefName

Źródła: GitHub CLI: fork i remotes, logowanie przez przeglądarkę, uwierzytelnienie Git.

Agent w CI/CD: Azure, GitLab, Bitbucket

Przykłady do konfiguracji w repozytorium kursu: agent robi code review i security review każdego pull requestu, dodaje komentarz do PR, czyta zadanie z Jira i dopisuje tam wynik. Agenta wybierasz jedną zmienną: Copilot, Claude Code, Codex albo OpenCode.

  • Pipeline'y: Azure Pipelines, GitLab CI i Bitbucket Pipelines; dla GitHub Actions osobne przykłady w tym samym folderze.
  • Dostęp: uwierzytelnienie należy do konkretnego CLI i dostawcy. Administrator dodaje właściwy token jako sekret CI; sam klucz OPENROUTER_API_KEY nie loguje wszystkich agentów.
  • Obraz: własny, na Debian slim z czterema CLI. Alpine odpada, bo narzędzia agentów zakładają glibc.
  • Bitbucket: App passwords wycofano 28 lipca 2026; użyj API tokena z uprawnieniami wymaganymi przez integrację.

Źródła: Copilot CLI programowo, Claude Code headless, Codex exec, Bitbucket: wycofanie app passwords, Bitbucket: API tokens.
