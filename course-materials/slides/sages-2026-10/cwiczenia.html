Główna ścieżka Java

Od analizy kodu do sprawdzonej zmiany

1. Poznaj oryginalne repozytorium

Pracuj w osobnym klonie jFTP. Instrukcja · cały proces P18 · slajdy.

  1. Zapisz commit i stan Git, sprawdź dostępne narzędzia.
  2. Użyj P20: pakiety, entry pointy, zasoby, zależności i importy bez definicji.
  3. Porównaj wskazania Codex i Copilot CLI z oryginalnym kodem.
  4. Zapisz pierwszy błąd budowania, dowody i niewiadome. Na tym etapie bez napraw.

Wynik: mapa w docs/discovery/ w repo aplikacji, lista przeczytanych obszarów i polecenie z rzeczywistym wynikiem.

2. Zmierz i ogranicz kontekst

P21: pełna i skompresowana paczka tych samych plików Java/POM, potem paczka małego podsystemu. Porównaj jedną metodę z oryginałem. Kompresja usuwa część logiki, nie tylko formatowanie.

Wynik: zakres, wersja, commit i tokeny każdej paczki; przykład brakującej logiki. Agenci pobierają fragmenty potrzebne do pytania.

3. Podziel czytanie między agentów

P22: zacznij od dwóch rozłącznych obszarów. Brief określa ścieżki, zależności, format wyniku i osobny raport. GPT-6 Luna może czytać i streszczać; GPT-6.1 Sol syntetyzuje wynik. Sprawdź model faktycznie użyty przez narzędzie.

Wynik: raporty z sygnaturami, callerami, pokryciem i niewiadomymi. Sprawdź pięć twierdzeń każdego workera w źródłach. Zapisz dostępne statystyki zużycia.

4. Zbuduj wiedzę o frameworku

P23: krótka mapa i dwie karty rzeczywistego API. Sygnatura, użycie w aplikacji, błędy i dowód: repo, commit, plik, linie, symbol, hash.

Wynik: następny agent rozumie granicę aplikacja/framework i wie, które źródło doczytać. Gdy źródeł brakuje, karta zawiera obserwowane użycie i pytania, bez wymyślonych metod.

5. Zapisz proces jako skill i sprawdź nową sesję

P24: tworzymy legacy-repository-discovery. Nowa sesja dostaje mapę i karty, nie poprzednią rozmowę ani cały kod. Trzy pytania o zmianę, jedno o nieistniejące API.

Wynik: skill sprawdzony na zadaniu, poprawne cytowania i lista braków. Po rzeczywistej zmianie kodu wykryj oraz odśwież stare dowody.

6. Test charakterystyki i minimalna naprawa startu

P25: wybierz małe zachowanie bez GUI. Sprawdź wymagania kompilacji, przygotuj minimum do testu, zapisz obecne zachowanie i potwierdź, że test wykrywa tymczasową mutację. Cofnij mutację.

Potem naprawiaj kolejne błędy oryginalnego projektu. Każda zmiana ma przyczynę, mały diff i sprawdzenie. Kompilacja, test, Swing i transfer to osobne wyniki. Bez GUI zapisz ograniczenie; transfer tylko lokalny i syntetyczny po uzgodnieniu zakresu.

Wynik: własny test, raport diagnozy, uzasadnione zmiany i dowód startu albo dokładny pozostały błąd.

7. Jedna funkcja z PRD, ADR i review

Wejście: instrukcja jFTP · pełny prompt P19. Zarezerwuj kilka bloków pracy z przerwami; pojedynczy wycinek ogranicz do 30-60 min.

  1. W jFTP uzgodnij problem i kryteria jednej zmiany. Użyj P26 z write-prd i write-adr; dokumenty powstają w repo aplikacji.
  2. Agent pobiera aktualną dokumentację do użytych bibliotek. W planie P19 podaj faktyczny PRD, ADR, testy i właścicieli plików.
  3. Ustal role java-developer, repository-analyst oraz qa-reviewer. Deleguj tylko niezależne zadania.
  4. Odtwórz brak funkcji lub błąd testem. Implementuj, uruchom testy i refaktoryzuj przy zielonym wyniku.

Wynik i sprawdzenie: mały diff, test ujawniający problem przed zmianą i wynik ponownej walidacji.

Gdy utkniesz: pokaż polecenie i dokładny błąd, zachowaj diff, zmniejsz zakres i zapisz kolejny krok. Analiza oraz przegląd istniejącego kodu pozostają użyteczne przy blokadzie dostępu.

3. Weryfikacja, review i pull request

Wejście: course-materials/cicd-headless · pełny prompt P08. Zarezerwuj kilka bloków pracy z przerwami; pojedynczy wycinek ogranicz do 30-60 min.

  1. Sprawdź testy jednostkowe, integracyjne oraz rzeczywisty scenariusz Java odpowiedni do zmiany.
  2. Użyj pełnego P08 na swoim diffie. Niezależny reviewer czyta AC i kod; uczestnik weryfikuje uwagi.
  3. Popraw rzeczywisty błąd i ponów walidację. Przeglądarka jest opcjonalna dla aplikacji z web UI.
  4. Po lokalnym sprawdzeniu przygotuj PR: zachowanie przed/po, zakres testów, ryzyka. Cloud i pipeline sprawdź w zatwierdzonym środowisku.

Wynik i sprawdzenie: review powiązany z AC, rzeczywisty wynik testów i gotowy PR albo jasno opisany stan niedokończony.

Gdy utkniesz: pokaż polecenie i dokładny błąd, zachowaj diff, zmniejsz zakres i zapisz kolejny krok. Analiza oraz przegląd istniejącego kodu pozostają użyteczne przy blokadzie dostępu.

4. Copilot CLI i wspólny standard

Wejście: .github · pełny prompt P03. Zarezerwuj kilka bloków pracy z przerwami; pojedynczy wycinek ogranicz do 30-60 min.

  1. Sprawdź wersję, logowanie, model i zakres zgód Copilot CLI. Uruchom zadanie na tym samym kodzie Java.
  2. Pliki .github/agents/*.agent.md są wzorcami do adaptacji, nie rozwiązaniem zadania. Dostosuj jedną małą rolę do swojej zmiany i zweryfikuj wspólne AGENTS.md oraz instrukcje GitHuba.
  3. Sprawdź skill i nieszkodliwy hook, omów dystrybucję pluginu. Porównaj zadanie interaktywne, -p i dostępny cloud agent.
  4. Przygotuj mapę: zadanie, wybrane narzędzie, uprawnienia, test, koszt/limit i odbiór wyniku. Pokaż standard grupie.

Wynik i sprawdzenie: działająca wspólna reguła w obu CLI, porównany diff i konfiguracja gotowa do dalszej pracy.

Gdy utkniesz: pokaż polecenie i dokładny błąd, zachowaj diff, zmniejsz zakres i zapisz kolejny krok. Analiza oraz przegląd istniejącego kodu pozostają użyteczne przy blokadzie dostępu.

4.2 - własna rola, skill i granice rozszerzeń

Wejście: aktualny PRD małej zmiany, wskazany plik Java i test, wzorce w .github/agents/, zainstalowany skill oraz dokumentacja wersji Copilot CLI.

  1. Wybierz małe zadanie, np. analizę jednego kontraktu bez edycji. Dostosuj opis, dozwolone narzędzia i wynik jednej roli *.agent.md; nie kopiuj uprawnień implementatora do recenzenta.
  2. Wybierz rolę przez /agent lub --agent. Poproś o wskazanie zastosowanych instrukcji i plików. Sprawdź listę ról wbudowanych w tej wersji. Porównaj z jedną z nich; przy braku takiej roli zapisz ograniczenie.
  3. Uruchom skill na tym samym zadaniu i sprawdź jego wykrycie oraz wynik. Dla hooka przygotuj nieszkodliwy odczyt dozwolonego pliku i próbę zablokowanego zapisu do pliku testowego; zachowaj komunikaty oraz diff.
  4. Sprawdź dostęp do pluginów i zatwierdzonych źródeł. Jeśli polityka lub wersja nie pozwala na hook, plugin albo wybranego agenta wbudowanego, zapisz ograniczenie i pokaż plan konfiguracji; nie instaluj obejścia.

Wynik: jedna własna rola do małego zadania, raport z jej uruchomienia, dowód wykrycia skilla i tabela: rozszerzenie, dostęp, zakres, wynik próby.

Weryfikacja: odpowiedź odwołuje się do wskazanego kodu i AC, zakres narzędzi odpowiada roli, niedozwolony zapis nie powstał. Rozdziel wykonany test od opcjonalnego planu dystrybucji pluginu.

4.3 - issue, review i odbiór pull requesta

Wejście: własny branch z małą zmianą Java, aktualny PRD/AC, rzeczywisty diff i wyniki testów oraz konto z zatwierdzonym dostępem do repozytorium. Użyj fikcyjnego zadania, bez danych firmy.

  1. Powiąż issue albo lokalny opis zadania z AC. W sesji Copilot wykonaj niezależny review pełnym P08; porównaj go z zadaniem copilot -p z minimalnymi sprawdzonymi zgodami.
  2. Popraw trafną uwagę i ponów rzeczywiste testy. Przygotuj opis PR: zachowanie przed i po, zakres, polecenia z wynikami, ryzyka i jawne luki. Fork oraz GitHub CLI są tu opcjonalnym sposobem obsługi PR.
  3. Jeżeli masz dostęp, zleć cloud agentowi ten sam mały zakres i odbierz draft PR. Odróżnij cloud agenta przygotowującego PR od zdalnej sesji CLI copilot --cloud. Bez dostępu przejrzyj lokalny diff i przygotuj opis draftu.
  4. Porównaj proponowane zmiany z AC, wynikami lokalnych testów i statusem CI. Omów mapowanie issue/PR na Jira oraz Bitbucket z przykładów biblioteki; nie łącz prywatnych systemów podczas labu.

Wynik: review z decyzjami po uwagach, opis PR oraz gotowy draft PR lub jawny lokalny checkpoint, jeśli publikację blokuje dostęp.

Weryfikacja: diff realizuje jeden uzgodniony zakres, testy po zmianie są sprawdzone, opis PR odpowiada dowodom. Brak dostępu cloud/CI nie jest wynikiem pozytywnego testu; merge wymaga osobnej decyzji właściciela repozytorium.

7. Modernizacja i interfejs

Dalsza praktyka legacy: pracuj na rzeczywistym projekcie JFTP z pełnym promptem P18. Poznaj kod, udokumentuj granice, dodaj test charakterystyki, napraw start i zmodernizuj jeden mały fragment. Gdy zabraknie czasu, wykonaj to jako pracę własną; rozszerz analizę rozpoczętą na kursie.

Wariant UI: użyj P05 na stronie, do której masz prawo dostępu. Porównaj wynik ze zrzutem, DOM i kontrolą klawiaturą.

Wynik: plan, mała próbka wykonania i niezależna weryfikacja.

Agenci w Twoim stacku: SQL, Pandas, Spark, ES, legacy

Opcjonalnie: wybierz wariant najbliższy Twojej codziennej pracy. Plik: pełny prompt do pracy z danymi

A - SQL (PG/Oracle/MSSQL)

Eksploracja schematu + ERD, analiza z weryfikacją drugim zapytaniem, EXPLAIN i indeksy, migracja dialektów (PL/SQL i T-SQL -> Postgres)

Audyt jakości danych, TDD na funkcjach transformacji (pytest przed kodem), raport z wykrywaniem ukrytych wzorców

C - Spark / Scala

Pandas -> PySpark z uzasadnieniem wyborów, dokumentacja i refactoring legacy joba Spark

D - Elasticsearch

Mappings + Query DSL z języka naturalnego (agregacje), walidacja bez klastra lub bulk-load na testowym

E - Legacy (Delphi/C#)

Dokumentacja + testy charakteryzacyjne (golden master) + plan migracji własnego modułu

Zasada bezpieczeństwa: nigdy nie podłączaj agenta do produkcyjnej bazy - dane syntetyczne lub kopia, użytkownik read-only, reguły deny w /permissions.
